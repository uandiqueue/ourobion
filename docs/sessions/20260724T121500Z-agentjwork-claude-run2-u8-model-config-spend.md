## What was built

### 1 · Migration `supabase/migrations/20260724130000_create_o10_llm_router_boundaries.sql`
- **`llm_router_status`** (node pk): model_id, route, max_output_tokens, per_day_usd_cap,
  per_run_token_cap, hard_stop_fraction, test_mode, test_mode_reason, published_at. Table comment
  says it verbatim: PROJECTION of `tools/llm-router/router.config.json` — rebuildable, never
  hand-edited; source of truth stays the file (two-tier truth).
- **`llm_router_spend`** ((day, node) pk): calls, tokens_in, tokens_out, usd `numeric(14,8)`
  (8 dp because U1's real smoke entry is 0.00015125 — 6 dp would round it away), published_at.
  Same projection comment; freshness is publish-driven and consumers must say so.
- **`llm_router_cap_overrides`** (node pk, CHECK node ∈ the six LLM_NODE_IDS): nullable
  per_day_usd_cap / per_run_token_cap, updated_by uuid, updated_at. **CHECK bounds:**
  `per_day_usd_cap > 0 and <= 5.00` (the run budget is hard-capped ~14.7 USD total — a UI typo
  must not blow it; **C-entry candidate**), `per_run_token_cap > 0 and <= 200000` (C7's
  originally-shipped per-run ceiling).
- **RLS:** authenticated SELECT on all three; authenticated INSERT/UPDATE on cap_overrides ONLY
  (dev-only posture per this run's D3 precedent), both `with check (updated_by = auth.uid())` so
  the audit column cannot be forged; no DELETE (clear = NULL the field); service_role publishes
  status/spend (bypasses RLS — no write policies on the projections on purpose).

### 2 · Publisher (router side)
- `tools/llm-router/src/publish.ts` — pure `buildStatusRows(config, ledger, publishedAt)` →
  `{status, spend}` row arrays (offline unit-testable; `LedgerFile` now exported from budget.ts).
- `tools/llm-router/scripts/publish-status.ts` (tsx-run, smoke-openai style) — loads
  router.config.json + the ledger file, upserts both tables via PostgREST
  (`Prefer: resolution=merge-duplicates`, `on_conflict=node` / `day,node`) with the service key.
  **Env sourcing (documented in the script):** process.env first, then `apps/nao/.dev.vars`
  (generated by apps/nao's gen-env from apps/nao/.env — the U6 server-env convention; locally
  the values are what `npx supabase status` prints). Publishing is an EXPLICIT script this
  cycle — the router does NOT auto-publish per call (**candidate improvement**: piggyback a
  publish on `record()` or a cron).

### 3 · Override consumption (router side) — the seam
- `tools/llm-router/src/overrides.ts` — `fetchCapOverrides()` (PostgREST GET, 4s abort,
  bounds re-validated row-by-row: out-of-bounds / unknown-node values ignored with warnings) and
  pure `effectiveCapsFor(config, overrides, nodeId)`.
- **Semantics:** an override REPLACES the file cap for its node (may lower or raise, bounded at
  5.00/200000 twice — DB CHECK + client re-check). The config's caps stay global-per-config
  (smallest correct change): `BudgetLedger` now takes `overrides` and resolves EFFECTIVE
  per-node caps at spend-check time in `wouldExceed`/`assertCanSpend` (refusal messages name the
  active override). The per-run token counter stays run-wide; the override changes the ceiling it
  is checked against for the overridden node's calls.
- **Entry points:** `LlmRouter.create()` (async factory: fetch fail-soft → construct; the sync
  constructor never touches the network) and the CLI — `check-config`/`ledger` fetch overrides
  fail-soft and pass them into `checkConfig` (new `capOverrides` option; `NodeReportRow` gained
  effective-cap fields). check-config prints `dayCap=US$X*`/`runCap=Y*` per node plus a
  `Cap overrides` section.
- **FAIL-SOFT:** absent env or unreachable/erroring Supabase → `undefined` (file caps) + ONE loud
  warning; never a throw. The router cannot be bricked by the boundary.

### 4 · nao `/models` (SubNav tab "Models")

## Decisions / notes for retro-review

- **O10(c) deliberately deferred:** the ingestion-progress + source-catalog + run-history
  boundary is NOT built this cycle — nao's existing Overview covers the demo (per the U8 brief;
  recorded as a deliberate deferral, still open on O10).
- **Bound choices:** per_day_usd_cap <= **US$5.00** (C-entry candidate; protects the ~14.7 USD
  run budget), per_run_token_cap <= **200000** (C7's shipped per-run ceiling). Staleness
  threshold **1h** (publish-driven snapshot honesty).
- **Override semantics:** replace-not-min per node, resolved at spend-check time in BudgetLedger;
  config file structure untouched. Overrides can RAISE a cap up to the bound — deemed correct
  for the demo (that is what "editable caps" means) with the ceiling as the safety.
- **usd precision:** numeric(14,8) so sub-cent real spend survives the projection.
- **Candidate improvement:** auto-publish (ledger `record()` hook or cron) instead of the
  explicit publish script; left out on purpose this cycle per the brief.
- Publishing/consumption keys: service key only (`SUPABASE_SERVICE_ROLE_KEY`); the overrides
  SELECT policy is `authenticated`, so an anon-key reader would see nothing — the router is a
  backend process and uses the service key by design.
